# 三种列存文件格式的区别：Parquet、Doris、Lance

> 随笔。把 Parquet、Doris（segment v2）、Lance（v2.1）三种列存文件格式的区别，
> 归到两个动作上讲清楚：**点查（定位第 i 行）** 和 **扫描（读一整列）**。
> 我发现这两个动作最后都落到同一组量上，各种编码、压缩、自适应编码，都是在这组量上
> 做取舍。数字部分尽量给具体的。

## 先把问题归到两个动作

一个列存文件，无非被两种方式访问：

- **点查**：给一个 row id，把这一行（的某些列）取出来。向量检索、倒排检索给回 row id 后
  的"取数"就是这种。
- **扫描**：从头到尾读一整列（或几列）。分析型查询的主力。

三种格式的所有差别，用这两个动作加几个数字就能讲透。

## 洞察一：定位第 i 行，本质要回答三件事

取第 i 行某列的值，本质上要回答三个问题：

1. **它落在哪一块？**（这一列被切成很多"块"，第 i 行在第几块）
2. **那块从文件的哪个字节开始？**
3. **在块内它是第几个？**

**索引，就是用来廉价回答前两件事的东西**；第三件事要么靠"把这一块解开、数到第几个"，
要么——如果编码允许——直接按位置算出来。

于是**点查的代价 ≈ 一块有多大（要解开多少）＋ 查一次索引**。块越小，点查越快。

这个视角很好用：后面会看到，各种编码、压缩、自适应编码，全都是在"这三件事怎么答得更便宜"
上打转。

## 洞察二：扫描的开销跟块数有关，但有多大由硬件定

有人会说：块切这么小，随机 I/O 不就多了、扫描不就慢了？扫描时 I/O **调度器**会把相邻字节
区间**合并成大读**、并发发出去，确实能大幅削掉随机 I/O。但要注意，它**只能合并物理上相邻的
块**，并没有把"块数"这件事彻底抹掉。块数通过**两条通道**影响扫描：

**通道一（CPU，与硬件无关）：每块固定开销 × 块数。** 每处理一块都要解析块头、初始化解压、
跳过元数据。块越多，这笔累积越多。

**通道二（I/O，对硬件敏感）：物理碎片 × 每请求成本。** 一列的数据若被切散（和别的列交错、
或被 row group 打散），就形成多个**不连续的段**，每段至少一次读。碎片越多、每段越小，读请求
越多。而一次读的代价，**完全看硬件**：

- **NVMe SSD**：随机读吞吐 ≈ 顺序读吞吐（100 万 IOPS × 4KB ≈ 3~4 GB/s，跟顺序带宽同量级），
  一次请求 50 ~ 100 µs。**碎片再多也不太亏**——块数在这里主要体现为通道一的 CPU 开销。
- **对象存储 S3**：一次 GET 30~100 ms，且随机（很多小 GET）比顺序（少数大 GET）慢好几个
  数量级。**碎片非常贵**——要么发很多昂贵的 GET，要么把间隙桥接起来多读些废数据。

**同一份碎片，在 S3 上的代价约是 NVMe 的上千倍**（每请求 ~50 ms vs ~50 µs）。本质区别是：
**NVMe 把随机/顺序的差距抹平了，S3 把它放大了。**

所以"扫描能力是不是取决于 page 数量"——**有关，但代价有多大由硬件决定**。精确地说：

> **扫描 ≈ 总字节（压缩比）＋ 每块开销 × 块数（CPU）＋ 物理碎片 × 每请求成本（I/O，硬件敏感）。**

而好格式会让**每个物理段足够大**，这样逻辑上切得再细，读起来仍是大块顺序 I/O。Lance 的 writer
按每列 ~8 MiB 攒一段落盘，正是这个用意：**8 MiB 在 NVMe 上是高效顺序读、在 S3 上也是一个划算
的 GET 大小，两边都不亏。**

## 两个洞察合起来：一个统一的框架

把两件事并排看，一列被切成"块"，就有两个旋钮：

| 旋钮 | 调大 | 调小 |
|------|------|------|
| **块大小** | 扫描省心（块少），点查亏（解得多） | 点查快（解得少），但块变多 |
| **每块开销**（索引条目 + 块头 + 元数据） | —— | 必须尽量小，否则块一多，扫描被拖累 |

于是理想的格式是：**块尽量小（点查赢），同时每块开销尽量小（这样块多了扫描也不亏）。**

而"每块开销小"靠的就是**便宜的索引/元数据**。所以一句话：

> **便宜的元数据，是同时赢点查和扫描的钥匙——它让你敢用很多个小块。**

这也解释了为什么不能简单"把 page 调小就行"：如果每块开销很重，块一多，扫描的 CPU 开销和
元数据体积都会爆（通道一）。谁的每块开销便宜，谁才敢把块做小。至于 I/O 那条通道（物理碎片），
靠的是**让每个物理段够大**来压住——在 S3 上尤其要紧，在 NVMe 上则宽松得多。

## 三种格式落到这个框架

现在把 Parquet、Doris、Lance 放进"块大小 + 每块开销"这两个量里。

### 每块开销（回答"哪一块、从哪开始"的成本）

- **Parquet**：每个 page 挂一个 **PageHeader**（thrift 编码：类型、编码、值数、压缩/未压缩
  大小、min/max 统计……几十字节，还要逐个解析），外加可选的 OffsetIndex 每 page 一条。
- **Doris**：每列一张 ordinal 索引（行号 → page），每条约 **16~24 字节**（首行号 + page 指针），
  再加每个 page 一个 page footer。
- **Lance**：mini-block 每块 **2 字节**（`(压缩字节/8 − 1) << 4 | log2(值个数)`）；full-zip 每值
  一个 **0/1/2/4 字节**的控制字。

**每块开销：Parquet 几十字节 ≫ Doris 十几二十字节 ≫ Lance 2 字节。** 差一到两个数量级——
这决定了各自"敢把块做多小"。

### 块大小 + 点查要解多少（回答"块内第几个"的成本）

取一个 **embedding**（一行 4 KB）：

| | 块大小 | 一块装几个 embedding | 取 1 个要解 |
|---|---|---|---|
| Parquet | ~1 MB page（被大小卡住） | 256 | **256** |
| Doris | 64 KB page | 16 | **16** |
| Lance | full-zip 直接定位 | —— | **1** |

取一个 **int**（一行 4 B）：

| | 块大小 | 一块装几个 int | 取 1 个要解 |
|---|---|---|---|
| Parquet | ~80 KB page（被 2 万行上限卡住） | 2 万 | **2 万** |
| Doris | 64 KB page | 16384 | **16384** |
| Lance | 8 KiB mini-block | 2048 | **2048**（或走 full-zip = **1**） |

两张表读出几件事：

- **窄列（int）上，Parquet ≈ Doris**（2 万 vs 16384，都被卡在几十 KB 一块），Lance 的 8 KiB
  mini-block 好约 8 倍，但仍是"解一整块"的模型——**对 int，Lance 的 mini-block 就是个更小的
  压缩 page**。
- **宽列（embedding）上差距才拉开**：Parquet 的 page 被撑到 1 MB（解 256 个），Doris 64 KB
  （解 16 个），Lance full-zip 直接定位（解 1 个）。

### 反过来看扫描：宽列暴露了 Doris 的小 page 代价

用"块数 × 每块开销"看扫描一个 **embedding 列**（100 万行）：

- **Parquet**：1M / 256 ≈ **4000 个 page**，每个 PageHeader 几十字节。
- **Doris**：1M / 16 ≈ **62500 个 page**。每个 page 都强制带一个 footer（序列化的
  `PageFooterPB` + 4 字节 footer 大小 + 4 字节 crc32c 校验），另加一条 ordinal 索引（首行号 +
  page 指针）——合计**每 page 约三四十字节**。
- **Lance**：块很多，但每块 **2 字节**。

Doris 为了点查把 page 缩到 64 KB，代价是宽列上 page 数暴涨到 6 万多，每 page 三四十字节的
元数据累加起来（62500 × ~35B ≈ 2 MB），一列光元数据就上 MB；而且扫描时这 6 万多个 footer 还要
一个个 protobuf 解析、逐 page 校验 crc、初始化解压。**这正是通道一
（块数 × 每块开销，CPU 侧）在起作用**：Doris 每块开销不够便宜，所以块一多，CPU 和元数据就
开始亏（这条通道跟硬件无关，NVMe / S3 上都亏）。Lance 每块 2 字节，所以块再多也不心疼——它
能同时把块做小（点查赢）又不让扫描亏。

### 一张总表

| | 块大小 | 每块开销 | 点查（embedding） | 扫描 CPU 开销（块数×每块） |
|---|---|---|---|---|
| Parquet | 大（~1 MB） | 重（PageHeader 几十字节） | 差（解 256） | 块少、每块重 |
| Doris | 中（64 KB） | 中（索引 16~24 B + footer） | 凑合（解 16） | 宽列块多、每块中等 |
| Lance | 小（8 KiB / 单值） | 极小（2 字节 / 0~4 字节） | 好（解 1~2048） | 块多但每块极小 |

（这张表是 CPU 侧；I/O 侧还有"物理碎片 × 每请求成本"一项，在 S3 上放大、在 NVMe 上可忽略，
取决于每列数据被切得多散、每个物理段多大。）

## 那编码、压缩、自适应编码是什么？都在这个框架里做取舍

有了"三件事 + 块大小 + 每块开销"这个框架，就能把各种花样归位：

- **压缩**：把总字节压小（扫描省字节），但它把值**绑进块**——点查要解整块才能拿一个。所以
  压缩天然和点查冲突，靠"块大小"来平衡。**压缩的粒度 = 块的粒度**，这是矛盾的根。
- **编码**（bitpacking、RLE、字典、frame-of-reference）：让"块内解码"更快或更省。其中一部分
  编码（比如定长 bitpacking）让"块内第几个"能**直接算位置**——于是第三件事从"解整块"变成
  "免费"。所以**编码的一个隐藏作用，是决定第三件事贵不贵**。
- **自适应编码**（Lance 的核心）：按列在两条路之间选——
  - **不透明块（mini-block）**：压缩比好，但取一个要解整块；
  - **透明可寻址（full-zip / 定长 stride）**：直接算位置取一个值，但放弃不透明块压缩。

  本质上，**自适应编码就是"按列决定第三件事（块内定位）是解整块还是直接算"**，在压缩比和
  点查速度之间按列各选各的。Doris 也按列选编码，但它的选择改不了"整块压缩 + page 级索引"这个
  底盘，所以选来选去还是解一整个 page。

## 定长宽列（embedding）为什么最能说明问题

embedding 是定长（4 KB/行），第 i 行的位置就是 `i × 4KB`——**三件事里的第三件天生 0 成本**，
它本来是最容易随机访问的数据。可 Parquet 偏偏把它裹进 1 MB 的 page + 整块压缩（浮点还压不动），
把本来能直接算位置的数据变成"要解 256 个"。Lance 的 full-zip 定长走 stride，把第三件事还原成
免费，于是三件事又都便宜了。**同一份数据，格式决定了它是"解 1 个"还是"解 256 个"。**

## 最后归到硬件：块大小的甜点由介质定

"块该多大"没有绝对答案，它由存储介质定：一次读的**固定开销 ÷ 每字节开销**，得到一个"一次读
多大才划算"的尺寸。

- **机械硬盘**：一次寻道 ~10 ms、带宽 ~150 MB/s，10 ms 能顺序读 ~1.5 MB → 划算尺寸 MB 级 →
  逼你用大 page。**Parquet 就是按这个设计的。**
- **NVMe SSD**：一次随机读 50~100 µs、每秒几十万到百万次 → 划算尺寸掉到 KB 级（4~64 KB）→
  小块变得可行。**Doris 64 KB、Lance 8 KiB / 单值，吃的都是这个红利。**
- **对象存储 S3**：一次 GET 30~100 ms 但可大量并发 → 偏好大块或大量并行 range 读，且元数据
  请求本身也贵 → 更看重"每块开销小"。

**便宜的元数据，让你能把块做到贴近 NVMe 的甜点，而不被块数拖垮。** 这就是 Lance 相对 Parquet
的时代差：Parquet 的 page 是机械硬盘时代调的，Lance 是按 NVMe / 向量检索场景重新调的。

## 结论

三种格式的区别，一句话收敛到三个量：**块多大、每块开销多小、块内定位要不要解整块。**

- **Parquet**：大块（~1 MB）+ 重每块开销（thrift PageHeader）+ 块内必须解整块。扫描最优、
  点查最差，而且**因为每块开销重，它不能把块调小**。机械硬盘时代的产物。
- **Doris**：中块（64 KB）+ 中每块开销（行号索引 + footer）+ 块内解整块。把 page 缩小、堆
  索引，做到"扫描格式也能凑合点查"；但宽列上小 page 让块数暴涨，扫描要还账。SSD 时代的务实
  折中。
- **Lance**：小块（8 KiB / 单值）+ 极小每块开销（2 字节）+ 块内可选"直接算位置"。因为每块开销
  便宜到 2 字节，它敢用很多小块，于是点查和扫描都拿到——这才是它相对前两者的真正分野。NVMe /
  向量检索时代。

而所有编码、压缩、自适应编码，都是在"这三件事怎么答得更便宜"这个前提下的取舍与优化——**压缩
决定块内要不要整块解、编码决定块内定位贵不贵、自适应编码把这个选择下放到每一列。**
