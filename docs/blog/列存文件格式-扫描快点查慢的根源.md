# 列存文件格式：扫描快、点查慢的根源，从 Parquet 到 Lance

> 这是一篇随笔，记录我对几种列存文件格式（Parquet、Doris 的 segment、Lance）的理解，
> 不是设计文档。核心想弄明白一件事：为什么这些格式扫描很快，但按行取数（点查）很慢，
> 以及新的格式是怎么改的。

## 从一个具体查询说起

先看一条查询：

```sql
SELECT id FROM t ORDER BY dist LIMIT 100;
```

假设 `dist` 是向量相似度，由一个独立的向量索引算出来。索引不在数据文件里，它只吐回
100 个 row id。接下来数据库要做的事，是**去数据文件里把这 100 行的 `id` 取出来**。

这就是一次典型的"点查"——按 row id 随机取少量行。注意即使这里只碰了一个很窄的 `id`
列，它仍然是 100 次随机取数。如果查询要返回的是每行的 embedding（一个几 KB 的大列），
那就是 100 次随机取几 KB 的大值。

我发现，Parquet 这类格式在这种访问方式上表现很差，而它扫描全表时又非常快。想搞清楚这个
差别从哪来，得先看 Parquet 当初是为什么造的。

## Parquet 是给什么场景造的

Parquet（2013 年，Twitter 和 Cloudera，思想来自 Google 的 Dremel）的目标场景很明确：
**HDFS 上、机械硬盘、只读的大规模分析数据，做整表/整列的顺序扫描**。

当时的硬件决定了一切：

- 机械硬盘一次寻道大约 **10 毫秒**，顺序带宽大约 **150 MB/s**。也就是说，10 毫秒里它能
  顺序读大约 **1.5 MB**。所以只要你随机读的东西小于 1 MB 左右，时间几乎全耗在寻道上——
  硬盘逼着你**一次读一大块**。
- I/O 是瓶颈，CPU 相对富余，所以用重压缩换 I/O 是划算的。

点查、随机取数**根本不在它的设计目标里**，那是 HBase 这类系统的活。所以一句话：
**Parquet 是个纯粹为"扫描 + 吞吐"设计的格式。**

## Parquet 的结构：三层

一个 Parquet 文件从大到小是三层：

```
文件
│
├─ Row Group 0  ────────────────────────────  第 1 层：一段连续的行 × 所有列，约 128 MB
│   │
│   ├─ Column Chunk(列A)  ──────────────────  第 2 层：这段行里，列A的全部数据，连续一块
│   │    ├─ Page 0  ───────────────────────   第 3 层：编码+压缩+解码的最小单位，约 1 MB
│   │    ├─ Page 1
│   │    └─ ...
│   │
│   ├─ Column Chunk(列B)
│   │    ├─ Page 0
│   │    └─ ...
│   └─ ...
│
├─ Row Group 1
│   └─ ...
│
└─ Footer  ──────────────────────────────────  每个 row group / 每列的位置、min/max 统计
```

也就是：**Row Group（切行）→ Column Chunk（切列）→ Page（列内再切小块）**，一层套一层。

- **Row Group**：一段行范围，包含所有列。约 128 MB，对齐 HDFS 的块，是扫描的并行单位。
- **Column Chunk**：一个 row group 内，某一列的全部数据，连续存一块。所以 row group 内部
  是"列A整块、然后列B整块"，**不是按行交错的**。
- **Page**：column chunk 再切成一个个 page，默认目标约 **1 MB**（或行数上限，比如 2 万行），
  **page 是编码、压缩、以及读取解码的最小单位**。

关键就在最后这句：**page 是一次至少要读进来、并且要从头解开的一整块。**

## 点查为什么慢：拿一行要解开一整个 page

取任意一行的某列值，流程是：找到这行落在哪个 page → 把这个 page 整块读进来 → 从 page 头
开始解压解码 → 取出第 (行号 − page首行) 个值。因为编码和压缩是按整个 page 做的，你**没法
跳到 page 中间**直接读某一行，必须整块解开。

用具体数字看一张 100 万行、有一个 int 列和一个 embedding 列的表（embedding 按 1024 维
float32 算，一行 4 KB）。page 在"大小到 1 MB"或"行数到 2 万"这两个条件里，先满足哪个就
切：

| 列 | 单值大小 | page 被哪个条件切 | 每个 page 行数 | 每个 page 大小 | 100万行的 page 数 |
|----|---------|------------------|---------------|---------------|------------------|
| int | 4 B | 行数先到（2万 < 1MB/4B） | 2 万 | 约 80 KB | 约 50 |
| embedding | 4 KB | 大小先到（1MB/4KB） | 约 256 | 约 1 MB | 约 4000 |

取一行时：

- **int 列**：读一个约 **80 KB** 的 page，解出 2 万个 int，只为拿 1 个。
- **embedding 列**：读一个约 **1 MB** 的 page，解出 256 个 embedding，只为拿 1 个。

## 一个反直觉的发现：宽列的"多读倍数"反而更小

我一开始以为"列越宽，点查越亏"。但按上面的数字算，"多读倍数"（读进来的字节 ÷ 真正需要的
字节）是：

- int：80 KB ÷ 4 B = **2 万倍**
- embedding：1 MB ÷ 4 KB = **256 倍**

**宽的 embedding 列，多读倍数反而小得多**（256 倍 vs 2 万倍）；从"白白解开了多少行"看也是，
embedding 白解 256 行，int 白解 2 万行。原因就是 page 被大小卡住时，宽列一个 page 装不下
几行。

当然要说清楚两个不同的数：

- **多读的倍数、白解的行数**：embedding 更小（256 倍 / 256 行）。
- **绝对读了多少字节**：embedding 读了约 1 MB，int 只读了约 80 KB——**宽列绝对读得更多，
  单次点查其实更慢**。

两句都对，只是量的口径不同。但这个反直觉的地方能说明一件重要的事：**点查慢不是"列宽"造成
的，是 page 这个模型造成的。** 如果"宽 = 慢"是因果，那宽列的多读倍数不该反而更小。真正的
原因是"page 是不可跳读的整块"，宽窄只是把这个数放大或缩小。

## 宽定长列和大字符串，各自哪里不合适

**宽定长列（embedding）最委屈**：它本身就是一个定长数组，第 i 行的位置就是 `i × 4KB`，
**天生可以直接算出位置、只读那 4 KB**。可 Parquet 偏偏把它裹进 page，取一行要读 1 MB、
解 256 个——**把本来能精确定位的数据，人为变得不能跳读了**。而且浮点数据压不动，page 压缩
对它几乎没用，等于白白多了一层封装。

**大字符串 / blob**：变长，需要一张"第 i 行从哪个字节开始"的位置表才能跳读；Parquet 存成
page 内的字节数组，取一个也要解整个 page。更麻烦的是，一个几 MB 的大 blob 可能比 page 目标
还大，把切分搞得别扭；而且查询哪怕只需要少数几行的 blob，扫描也会把它整列读出来——没有"用到
再取"的机制。

**访问模式对不上**：新场景是"外部索引给 row id，我去随机取那几行"。Parquet 扫描很强，随机
取数很弱，根子上就是 page 不能跳读，跟列宽没关系。

## 两种改法：Doris 和 Lance

**Doris 的做法：把 page 调小，再堆一堆索引。** 它的列存 segment 里，一个数据 page 默认只有
**64 KB**（Parquet 是约 1 MB，相差 16 倍），再配上：每列一张"行号 → page"的位置索引（能直接
定位到某行落在哪个 page）、每个 page 一份 min/max（谓词不匹配就跳过这 64 KB）、稀疏的
short-key 索引、以及主键索引加布隆过滤器做点查。

拿 embedding 点查对比：Doris 的 64 KB page 装 16 个 embedding，取一行读 64 KB、解 16 个；
Parquet 读 1 MB、解 256 个——**Doris 在这一步好 16 倍**。但注意它**没有放弃 page 模型**，只是
把 page 变小、加索引，做到"扫描格式也能凑合点查"。（顺带一提，Doris 最近的"V3"是把每列的
元数据外置、加了新的 plain 编码，解决的是**列特别多时元数据太重**，跟这里说的宽值随机访问不是
一回事。）

**Lance 的做法：把"定位"和"压缩"彻底分开。** Lance 是专门为"既要扫描、又要随机取数"的机器
学习/向量场景造的。它的关键几点：

- **不用 row group**。
- 随机取第 i 行：**定长列 1 次 I/O**（直接 `i × 宽度` 算位置），**变长列最多 2 次 I/O**
  （先查一张位置表，再读那个值）。
- 核心是把**怎么定位一行和怎么压缩值拆开**，不再绑在同一个 page 上。Parquet 把这两件事
  焊死在 page 里，所以你为了点查把 page 调小，就同时毁了扫描和压缩。Lance 提供两种存法：一种
  是每个值单独压、位置表照样能定位到单个值（给宽列和 blob 用）；另一种是切成 4~8 KB 的小块、
  块内压缩、再配一张块索引，取一行只解一个小块。
- 大 blob "用到再取"（引用一路传下去，最后才真读）。

代价也要说清楚：Lance 的编码系统更复杂；**压缩比跟 Parquet 大致持平，不是更好**；生态没
Parquet 通用。它论文里报的随机取数速度提升很大（默认 Parquet 每秒几千行、优化后每秒几十万行
这个量级），扫描则与 Parquet 相当。

把三者放在一条线上看：

- **Parquet**：大读取单位（page ~1MB），扫描最优、点查最差——机械硬盘时代的产物。
- **Doris**：中读取单位（page 64KB）+ 一堆索引，扫描好、点查凑合——SSD 时代的折中。
- **Lance**：按值 / 小块定位 + 定位与压缩分开，扫描好、点查原生——NVMe / 机器学习时代。

## 归到根子上：一次读多大才划算，由硬件决定

想了一圈，我认为这里真正决定一切的，是**"一次读多大才划算"这个尺寸，而它由硬件定**。

道理是：任何存储介质，一次读都有**固定开销**（寻道、一次请求的延迟、最小块、网络往返）加上
**按字节算的开销**（带宽）。固定开销除以每字节开销，就得到一个"划算的最小读取尺寸"——比它小，
时间全耗在固定开销上（这时你受限于每秒能发多少次读，也就是点查关心的 IOPS）；比它大，时间才
真花在搬数据上（这时你受限于带宽，也就是扫描关心的吞吐）。

三种介质的大致数字：

- **机械硬盘**：一次寻道约 10 ms，带宽约 150 MB/s。10 ms 能顺序读约 1.5 MB → **划算的最小
  读取尺寸是 MB 级** → 必须用大 page。**Parquet 就是在这个前提下设计的。**
- **NVMe SSD**：一次随机读延迟约 50~100 µs，每秒能做 50 万~100 万次随机读，带宽 3~7 GB/s。
  读 4 KB 和读 64 KB 的延迟差不多 → **划算的最小读取尺寸掉到 KB 级（4~64 KB）** → 小 page、
  精确定位就变得划算。**Doris 的 64 KB、Lance 的 1~2 次 I/O，吃的都是这个红利。**
- **对象存储（S3）**：一次 GET 延迟约 30~100 ms，但可以同时发上千个。每次 GET 都有固定开销
  → 偏好"要么一次读一大块（≥1 MB），要么大量并行的 range 读"，而且**元数据请求本身也很贵**
  （这就是为什么宽列时 Parquet 的元数据能占到每十亿行几十 GB 内存，而 Lance 把它压到每个小块
  约 24 字节这么小很重要）。

## 我的结论

绕了一圈，我把它归成两句话：

1. **点查和扫描的矛盾，本质是"一次读多大才划算"这个尺寸的选择，而这个尺寸由硬件定**：机械硬盘
   逼你用 MB 级大块（扫描友好、点查最差），NVMe 允许你用 KB 级小块（点查也能很快）。Parquet
   的 page 是按机械硬盘调的（约 1 MB），放到 SSD 上做点查，就落在了最不划算的点上。Page 大小的选择本质**在同一条取舍曲线上选哪个点**。

2. **但不止于选点，Lance 证明还能换一条更好的曲线**：Parquet 用**一个** page 同时当"定位单位"
   和"压缩单位"，一个旋钮服务两个目的，注定两头不讨好。Lance 把**定位和压缩拆开**，让"精确定位
   到一行"和"按块压缩"各调各的——于是它能在随机取数快很多的同时，扫描和压缩都不吃亏。这一步
   **跟硬件无关，是设计上的选择**。

而列的宽窄，只决定这个矛盾有多痛，以及你需要的是"按固定宽度直接算位置"（定长列，比如 embedding），
还是"查一张位置表"（变长列，比如大字符串）。宽定长列尤其冤——它本来最容易随机访问（一次算位置、只读那几 KB），却被 page 模型搞成了最慢的那个。
