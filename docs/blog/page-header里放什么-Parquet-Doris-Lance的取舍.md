# page 头里到底该放什么：从第一性原理看 Parquet / Doris / Lance 的取舍

> 随笔。列存文件里每个 page（Doris 叫法是 footer，作用一样）都挂着一小块元数据。
> 这篇只讨论一件事：**这块元数据为什么必须存在，里面该放什么，三种格式各自怎么取舍。**
> 先讲清"为什么需要"，再看 Parquet、Doris、Lance 分别放了什么、为什么。

## 一、为什么每个 page 都要有个头

先问最根本的：一个 page 就是文件里一段**压缩+编码后的字节**。reader 顺着索引或扫描落到这段
字节上，它面对的是一坨**看不懂的二进制**。要把它变回一列值，reader 必须先知道一组"**解码说明**"：

1. **怎么解释这些字节**——用了什么编码（plain / bitpacking / RLE / 字典……）、什么压缩（zstd /
   lz4 / 不压）。不知道就没法解。
2. **有多大**——压缩后多少字节（这段到哪结束 / 该读多少进来）、压缩前多少字节（解压要开多大的
   输出缓冲）。
3. **有几个值、是哪些行**——这段装了多少个值、覆盖的行号范围（好把"目标第 i 行"换算成"块内第几
   个"）。
4. **null 和结构**——有没有 null（null 位图多大）、嵌套/数组的结构信息。
5. **完不完整**——一个校验和，检测有没有损坏。

**所以 page 头的本质，是"跟着数据走的解码说明"。** 压缩+编码把值变成了不透明字节，头就是把它
解回来的那把钥匙。没有头，字节无法解读——这就是它必须存在的原因。

## 二、关键一步：这些说明按"怎么变化"分三类

上面那组说明，不是每一条都得**每块**存。按它们**怎么变化**，分三类：

- **整列都一样**：编码方式、值宽、压缩算法。一整列所有块用同一套 → **完全可以每列只存一次**。
- **能从位置推出来**：块的首行号（first_ordinal）——如果块是规则排列、每块值数已知，那"第 i 行在
  第几块"可以**算出来**，首行号不必存。
- **真正每块不同、又推不出来**：**压缩后的大小**——因为压缩比每块都不一样，这个数**必须每块存**。

于是有个很强的结论：

> **不可省的最小 page 头 ≈ 一个"压缩后大小"。** 其余每一条，都是"放哪"的**设计选择**——
> 塞进每块（自描述），还是抽出去（省字节）。

三种格式的区别，几乎全在"抽出去多少"。

## 三、头里其实还塞了第二种东西：跳过说明（统计）

除了"解码说明"，page 头里常常还塞一类东西：**per-page 的 min/max 统计**。它不是用来解码的，是用来
**跳过**的——带过滤的扫描（`WHERE x > 100`）时，如果一整块的 max 都 < 100，就整块跳过、根本不读。

这带来一个额外的取舍：**统计放每页 → 过滤扫描能精细跳过，但头变重；统计抽到单独的索引里 → 头轻，
但跳过要另查一张表。** 后面会看到，这也是三家分道的一个点。

## 四、取舍轴：自描述 ↔ 极简

把上面两节合起来，"头里放多少"就是一根轴：

**放得多（自描述）**：任何 reader 拿到一个 page 就能独立解开（跨引擎互操作）、能 per-page 跳过、
reader 逻辑简单、还能带 crc 抗损坏。**代价**：头重（几十字节 + 解析开销）→ 逼你把 page 做大（不然
头占比太高、块数太多）→ 点查差、宽列扫描元数据爆。

**放得少（极简）**：头便宜 → 敢把块做到很小 → 点查好、宽列也不亏。**代价**：得有更多外部机制兜底
（编码信息进列元数据、null 进单独一层、位置靠推算），reader 和格式**紧耦合**，完整性得靠别处保证。

**头的大小 = 前一篇说的"每块开销"**，它直接决定块能做多小，从而决定点查快慢和扫描的逐块 CPU 开销。
所以"头里放什么"不是实现细节，是**决定格式性格的旋钮**。

## 五、三种格式：逐级把东西抽出每页

三家其实是这根轴上**依次把更多东西抽出每页**的三个阶段。

### Parquet：全塞每页（自描述最大化）

每个 page 头（thrift 编码的 `PageHeader`）几乎把上面所有东西都带上：page 类型、**编码方式**、
def/rep level 的编码、压缩后大小、压缩前大小、值个数，以及**可选的 per-page 统计（min/max/null 数）**。
一个头几十字节，还要逐个 thrift 解析。

**为什么这么重**：Parquet 活在**异构生态**里——Spark、Impala、Hive、DuckDB…… 任何 reader 都得
能把一个 page**独立解开**，所以解码说明必须**自带**；per-page 统计则服务谓词跳过。自描述 = 互操作 +
可跳过。

**代价**：头重 → 逼它用大 page（~1 MB）→ 点查要解一整块（宽列一块 256 个 embedding），宽列扫描
page 数也不少。这是它机械硬盘/大扫描时代出身的必然。

### Doris：把"编码"和"统计"抽走了（中间点）

Doris 的每页 footer（`PageFooterPB` + `DataPageFooterPB`）里**没有**编码方式、**没有** per-page 统计。
它把：

- **编码** → 抽到列元数据（`ColumnMetaPB`，每列一次）；
- **统计** → 抽到单独的 **zone-map 索引**（可查询的一张表，不在页里）。

每页只留：page 类型、压缩前大小、**首行号 first_ordinal**、值个数、null 位图大小，外加 4 字节 footer
长度 + 4 字节 crc32c。**合计约三四十字节。**

**为什么这样选**：Doris **自己控制 reader**，不需要 per-page 跨引擎互操作，所以编码抽到列级就够；它
想要 zone map 是一张能查的索引，所以统计单列出去；它保留 first_ordinal 是为了**按行号随机访问**，
保留 crc 是因为**本地盘**要每页完整性。

**代价**：头比 Parquet 轻，于是敢把 page 缩到 **64 KB**，点查好了些；但每页还有三四十字节，宽列上
（一块只装 16 个 embedding）100 万行 = 6 万多个 page，元数据累加上 MB，扫描时这些 footer 还要逐个
protobuf 解析、逐页校验 crc。

### Lance：几乎全抽走（极简最大化）

Lance 的 mini-block 每块元数据就 **2 字节**：`(压缩字节/8 − 1) << 4 | log2(值个数)`——**只剩"压缩
大小"（12 位）+ "值个数的 log2"（4 位）**。其余全部抽出每块：

- **编码 / 值宽 / 压缩** → 列元数据，每列一次；
- **first_ordinal** → 不存，靠块位置 + 值数前缀和**推算**；
- **null / 嵌套** → 抽到单独的 **repdef（rep/def levels）层**，非空列零开销；
- **统计** → 单独的结构，不在块里；
- **crc / footer 定长框** → 每块没有，完整性交给更粗粒度或存储层（S3 有对象级校验）。

**为什么这样选**：它要把块做到 8 KiB 甚至单值，去贴 NVMe / 向量检索的随机访问——而这只有在每块
元数据便宜到 2 字节时才不会把扫描和元数据拖垮。

**代价**：机制更多（列元数据、repdef、推算位置都得实现对），reader 和格式紧耦合，完整性外移。

### 一句话概括三段

**Parquet 把解码说明和统计全塞每页（互操作、可跳过，但头重逼大块）；Doris 把编码和统计抽出去、
每页只留行号/大小/null/crc（自控 reader、可查 zone map，中等头配 64KB 块）；Lance 把能抽的全抽走、
每块只留一个压缩大小（极致小块随机访问，但换来紧耦合与外部机制）。**

## 六、收敛：头里放什么，决定了格式的性格

回到最根本的一句：一个压缩块必须带解码说明，否则解不开。区别只在**这些说明放在哪、每块重复多少**：

- 放每页多 = 自描述、互操作、能 per-page 跳过、reader 简单 → 但头重、逼大块 → **点查差**。
- 抽出每页多 = 头轻、敢用小块 → **点查好、宽列扫描省** → 但要更多外部机制、reader 紧耦合。

所以"page 头里该放什么"不是一个细节问题，它就是**块能做多小**这个总旋钮的另一种问法——而块能做
多小，前一篇已经讲过，直接决定了点查和扫描的全部性格。Parquet、Doris、Lance 只是在这根轴上，
按各自的时代（机械盘 / SSD / NVMe+对象存储）和定位（通用生态 / 自有引擎 / 向量检索），停在了
不同的点上。
